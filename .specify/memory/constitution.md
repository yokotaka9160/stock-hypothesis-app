# 株式取引 仮説検証サービス Constitution
<!-- Example: Spec Constitution, TaskFlow Constitution, etc. -->

## 基本原則

### I. 検証結果の正確性（最優先）
- 利用者に間違った検証結果を提示してはならない。
- テストは再現性の確認を中心に行う。同じ条件で2回以上実行し、結果が完全に一致することを確かめる。テストは実装の後に書く。期待値との比較は行わない。
- 根拠：間違った検証結果の提示は、このサービスで最も起きてはならない失敗であるため。

### II. 定量的な検証結果の提示
- 検証結果は、仮説に基づく取引シミュレーションの定量的な結果として示さなければならない。
- 検証結果を示すときは、次の情報を必ず一緒に表示しなければならない。
  - 検証した仮説
  - シミュレーションの対象期間
  - 検証内での総取引回数
- 根拠：検証結果を信頼して判断に使うため。

### III. 仮説の問題点の提示
- 検証結果とあわせて、仮説の問題点を示さなければならない。
- 問題点は、少なくとも次の観点から示す。
  - 取引を実行する時間帯
  - 取引を実行するトリガー条件
  - トリガー条件の数値（例：何％上昇で購入するか、現在値から何％上の価格で購入するか）
- 根拠：検証結果を信頼して判断に使うため。

### IV. 再現性
- 同じ条件で検証した場合、何度実行しても同じ結果にならなければならない。
- 例外：生成AIによる改善案の提案内容は、毎回同じでなくてよい。

### V. シンプルさ
- 機能は次の3つに限定する。これ以外の機能は作らない。
  1. 仮説の保存、編集、削除
  2. 仮説のシミュレーション検証結果の提示
  3. 仮説の問題点の提示
- 株価データの取得・保存は、「検証結果の提示」の内部処理として行い、利用者が操作する独立した機能としては作らない

## 追加の制約
- 実際のお金を用いた株式取引は行わない。
- 利用者は個人（開発者本人）のみとする。
- 有料のサービスは使わない。
  - 株価データは、無料で取得できるもの（yfinance）を使う。
  - 生成AIは、Gemini API の無料枠のみを使う。

## 開発ワークフロー
- 開発は spec → plan → tasks → 実装 の順に進める。
- 各段階で、開発者本人のレビューと承認を必須とする。承認なしに次の段階へ進んではならない。

## ガバナンス
- この constitution を変更するときは、変更理由を記録する。

## 変更履歴
- 2026-10-30：原則Vに、編集・削除を「仮説の保存」に含めることと、株価データの取得・保存の扱いを追加。
  理由：spec 作成時に、仮説の編集・削除が必要になり、原則Vと矛盾したため。また、再現性（原則IV）を守るために株価データを DB に保存する必要が生じたため。
- 2026-10-31：原則IVに生成AIの例外を追加。追加の制約を「有料のサービスは使わない」に変更し、
  Gemini API の無料枠の利用を明記。
  理由：問題点の改善案（時間帯・トリガー条件）を生成AIに提案させることにしたため。
- 2026-11-01：原則I の「計算の正しさは、最も厳しくテストする対象とする」を、再現性の確認を中心とするテスト方針に置き換え。同じ内容になった「テストを書くタイミング」「計算が正しいことを確かめる比較対象」の2行を削除。版を 2.0.0 に変更。
  理由：計算の正しさを期待値と比べるテストは行わず、同じ条件で結果が一致することの確認を中心にすると決めたため。原則の再定義にあたるため MAJOR とした。
