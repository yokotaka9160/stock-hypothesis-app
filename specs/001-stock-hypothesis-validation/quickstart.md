# Quickstart: 株式取引 仮説検証

起動と動作確認の手順。仕様の詳細は [spec.md](./spec.md)、データの形は [data-model.md](./data-model.md) を参照。

## 前提

- WSL（Ubuntu）と Docker Desktop（WSL 連携を有効にする）
- 無料の APIキー
  - Gemini API：Google AI Studio で発行する（必須。仮説の読み取りと改善案の提案に使う）
  - Alpha Vantage：https://www.alphavantage.co/support/#api-key で発行する（任意。yfinance で決算発表の時刻が取れない回だけ使う。未設定でも動くが、その回は検証に使われない）

## 1. 環境変数を設定する

```bash
cp backend/.env.example backend/.env
```

`backend/.env` に APIキーを書く。`.env` はコミットしない（`.gitignore` 済み）。

| 変数 | 内容 |
|---|---|
| `GEMINI_API_KEY` | Gemini の APIキー（必須） |
| `GEMINI_MODEL` | 使うモデル。空なら `gemini-3.5-flash` |
| `ALPHAVANTAGE_API_KEY` | Alpha Vantage の APIキー（任意） |
| `DJANGO_SECRET_KEY` | 空ならローカル専用の仮の値を使う |
| `DJANGO_DEBUG` | `true` / `false` |

## 2. 起動する

```bash
docker compose up -d --build
```

- 画面：http://localhost:5173/
- API の確認：`curl http://localhost:8000/api/health/` → `{"status":"ok"}`
- DB（SQLite）は Docker のボリューム `backend-data` に置かれ、コンテナを作り直しても消えない
- backend の起動時に、DB のマイグレーションが自動で行われる

**注意**

- `backend/.env` を変えたら、`docker compose up -d --force-recreate backend` でコンテナを作り直す（値はコンテナを作るときにだけ読み込まれる）
- `pyproject.toml`・`package.json` の依存を変えたら、`docker compose up -d --build` でイメージを作り直す
- 止めるとき：`docker compose down`（ボリュームは残る）。DB も消すときだけ `docker compose down -v`

## 3. 動作確認

### 仮説の保存・編集・削除（User Story 1）

1. 左セクションの入力欄に、仮説の文章を入れて［保存］を押す。例：

   > 決算発表時刻を含む1時間足の、1本前の1時間足が確定したときに、その1時間足の終値から +2% の価格で、逆指値で買う。市場前・市場後に買った場合は市場前の最後の1時間足の終値で全売却し、市場中に買った場合は市場中の最後の1時間足の終値で全売却する。

2. 読み取り結果（トリガー条件・購入条件・購入方法・売却条件）を確認し、必要なら % と購入方法を書き換えて保存する
3. 「保存した仮説」に、文章と読み取り結果の両方が表示されることを確かめる
4. 検証できる範囲（FR-025）の外の文章（例：「決算発表の5分前に買う」）を入れると、読み取れなかった項目と、範囲に合うように補った文章の提案が表示され、保存されないことを確かめる
5. ［編集］で文章を直して保存し直せること、［削除］で確認のあとに削除されることを確かめる

### 検証結果の表示（User Story 2）

1. 右セクションで仮説を選び、銘柄（例：`AAPL, NVDA`）・検証期間（初期値は直近1年）・購入金額を入れて［検証］を押す
2. 検証した仮説・検証期間・購入金額・総取引回数・損益額、銘柄ごとの結果、取引の明細が表示されることを確かめる
3. 存在しない銘柄（例：`ZZZZZZ`）を入れると、その銘柄が「検証不可」と表示され、合計に含まれないことを確かめる
4. 同じ条件でもう一度検証し、総取引回数・損益額・取引の明細が同じになることを確かめる（FR-011）。2回目はデータを取り直さないので速い

### 問題点の提示（User Story 3）

1. 検証のあと、左セクションの検証した仮説の下に、問題点（なければ「問題は未発見」）、改善案の順に表示されることを確かめる
2. 改善案に、数値の改善案（再検証の結果つき・過学習の注意書きつき）と、AI の提案3個（未検証の表示つき）があることを確かめる
3. 改善案の［この案で新しい仮説を作る］を押すと、入力欄に文章が入り、保存すると右セクションでその仮説が選ばれることを確かめる（FR-027）

## 4. テスト

```bash
cd backend && uv run pytest
```

- 再現性（同じ条件で2回検証して一致するか）、保存したデータが上書きされないか、検証中に外部のデータを取りに行かないか、Gemini の失敗で検証全体が失敗になるか、を確かめる（tasks.md の Phase 6）
- ネットワークは使わない（yfinance・Alpha Vantage・Gemini は差し替えている）
- Docker の中で実行する場合：`docker compose exec backend pytest`

## 困ったとき

| 症状 | 原因と対処 |
|---|---|
| 「Gemini の APIキーが設定されていません」 | `backend/.env` に `GEMINI_API_KEY` を書き、backend のコンテナを作り直す |
| 「Gemini の無料枠の上限に達しました」 | 時間をおいてやり直す。1日の上限は太平洋時間の午前0時にリセットされる |
| 「Gemini が混み合っているため…」（503） | Gemini 側の一時的な混雑。時間をおいてやり直す |
| 「検証期間の開始日は … 以降にしてください」 | 1時間足は直近730日分しか取れない。開始日を後ろにずらす |
| 「データが欠けている日があります」 | yfinance のデータが欠けている日。データがある分だけで検証している（FR-009） |
| 画面の表示が古いまま | ブラウザを再読み込みする |
